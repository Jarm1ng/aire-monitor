# macOS App Internals

This document describes how the SwiftUI macOS app, the menu bar monitor, and the desktop widget actually work: the build system, the multi-cluster architecture, the login flow and status protocol, the runtime layout, the snapshot collector contract, and the UI.

Leeds HPC Monitor monitors several Slurm clusters at once. Today these are AIRE and Calder. Every cluster-specific fact lives in one `ClusterProfile`, every cluster gets its own fully independent `ClusterSession`, and one `AppModel` coordinates what the clusters share: the university account, the route, the Keychain item, and the serialized sign-in chain. Rules that the app, the widget and the tests must agree on live once, in the `HPCCore` library.

## Build and Run

```bash
./scripts/install_app.sh              # release build, installs /Applications/Leeds HPC Monitor.app, opens it
./scripts/install_app.sh --uninstall  # removes the installed app again
./scripts/run_macos_app.sh            # development: release build of the app and the widget, then opens the app
./scripts/run_macos_app.sh --debug    # the same, debug configuration
./scripts/run_desktop_widget.sh       # the widget only (what the app's Widget buttons run)
```

All three are thin wrappers around `scripts/build_bundle.sh [--debug] [--open] [--for-install] PRODUCT...`, the only place that knows how a bundle is made. `run_macos_app.sh` and `install_app.sh` build both products in one `swift build` and repackage both bundles, so the widget never lags the app.

```text
.runtime/AIREMonitorApp.app      display name "Leeds HPC Monitor", bundle id local.aire.monitor
.runtime/AIREDesktopWidget.app   display name "Leeds HPC Widget", bundle id local.aire.desktop-widget, LSUIElement (no Dock icon)
```

The bundle identifiers predate the rename and are kept on purpose: the Keychain item, the notification permission and the saved window frames hang off them. The app is opened with macOS `open`, so it becomes the active foreground application and its text fields receive keyboard focus. When LaunchServices is unavailable (error -600 from a non-GUI session), the script starts the executable directly.

**Installing.** `scripts/install_app.sh [--debug] [--skip-build] [--no-open] [--force]` makes the app a normal Mac app:

- **Where.** `HPC_INSTALL_DIR` when set, otherwise the folder of the existing install, otherwise `/Applications`, or `~/Applications` (created, with a note) when `/Applications` is not writable for the account (`HPC_INSTALL_DEFAULT_DIR` replaces `/Applications`; the tests use it). Nothing runs with `sudo`. The folder is resolved to its real path (links followed, names spelled as stored), and an earlier install counts as the same one when it is the same bundle by device and inode, so `/applications` or a link to the folder never moves, or deletes, the install. The bundle is named `Leeds HPC Monitor.app` and keeps the identifier `local.aire.monitor`, so notifications, the Keychain item and the preferences carry over. Its path is recorded in `.runtime/installed_app_path`.
- **How.** It builds with `build_bundle.sh --for-install` (`--skip-build` installs the bundle already in `.runtime/`). It then copies the bundle with `ditto` into a staging folder next to the destination, checks it with `codesign --verify --strict`, and swaps it in. Both moves of the swap use `rename(2)`, so a folder that appears at the destination makes the move fail instead of receiving the bundle. If the swap fails, the previous install is put back, only into an empty place. If even that fails, it stays in the staging folder, which is then kept, and the error says where. Each staging folder carries its run's process id in its name and an `owner` file with the id and start time. Staging folders that a killed run left behind are unregistered and removed at the start of the next run (and by `--uninstall`); a previous install found in one, with nothing in its place, is put back first. A staging folder whose run is still going (its owner process runs and started when the file says), for example another checkout installing into the same folder, is left alone. Finally it registers the copy with LaunchServices (`lsregister -f`) and opens it, unless `--no-open` or `HPC_INSTALL_NO_OPEN=1` is given. An install whose stamp, executable and Info.plist already match is left alone and only brought forward. A path under the app's name that holds anything else, or is a symbolic link, is never overwritten.
- **Running copies.** A copy counts as running from a bundle when the kernel runs it from that bundle's executable: the executable path the kernel reports for the process (`proc_pidpath`) is the same file by device and inode, or the same path word for word, which still finds a copy whose bundle was replaced on disk after it started. A small helper on `/usr/bin/python3` (which the collector uses too, run with `-I`) lists this account's processes that way and keeps paths as bytes, so no locale can escape them; it only looks at processes whose executable is named `AIREMonitorApp` (the kernel reports the real file name even for a copy started through a link), so a hung network mount elsewhere cannot stall the check. So a copy started through a symbolic link (to the bundle, a folder above it or the executable itself), in another letter case, by the spelling an older install record used, or from a folder with a non-ASCII name is found too, while a process that merely names, reads or maps the file (`tail -f`, an editor, a viewer, an indexer) is not. A running copy that has to be replaced, and any copy still running from `.runtime/` or from an older install location, gets the standard quit request (`NSRunningApplication.terminate`, what the Dock's Quit sends). So `applicationShouldTerminate` can show the quit prompt for running terminals, transfers or a sign-in. The script waits up to `HPC_INSTALL_QUIT_TIMEOUT` seconds (default 120). If the copy is still running, the script stops with exit status 3 and changes nothing. With `--force` it sends SIGTERM instead, which skips the prompt. A copy running from `.runtime/` is asked before the build, because the build replaces that bundle: if it does not quit, nothing is built and it keeps running on its own bundle, still registered. Write access to the folder, to `.runtime/` and to a bundle that is replaced (one installed with `sudo` belongs to root) is checked before anything is asked to quit: the helper asks access(2) whether the account may delete every entry of the bundle (it is deleted after the swap) and reads the file flags. So a locked bundle (`uchg`), an ACL that denies deleting it or a bundle without write permission is refused with nothing changed. macOS may deny a process without the App Management permission write access to a running app's bundle until the app quits, so such a refusal by macOS itself (`EPERM` where the mode bits allow it) is let through while a copy runs from the bundle; the move after the quit is the real test. If a step after the quit fails, the app that was quit is opened again, unless `--no-open` is given. Right after the old install is moved aside, the script checks once more for a copy started since the quit; if one runs from it, the old install goes back in place and the script stops with exit 3, nothing installed.
- **One canonical app.** Once installed, `.runtime/AIREMonitorApp.app` is only the build output. `build_bundle.sh` replaces it without stopping or restarting anything, never opens it, and unregisters it (`lsregister -u`) instead of registering it. Before the first install (`--for-install` without an install record) it stays registered, and `install_app.sh` unregisters it only once the installed copy is in place, so a failed first install leaves the app launchable. That is its very last step, after opening the app, once no process runs from `.runtime/` (it waits up to 5 s for a copy that just quit to finish exiting). Every bundle the scripts delete is unregistered first, while it still exists: `build_bundle.sh` the bundle it replaces, `install_app.sh` the install it replaced or moved away from and the bundles in a staging folder. LaunchServices keeps the record of a bundle deleted while registered, under its old path, and `lsregister -u` on that path afterwards only reaches the new bundle there; that is how a first install once left the `.runtime/` bundle the app had been running from listed next to the installed copy. `run_macos_app.sh` hands over to `install_app.sh`, so it updates and opens the installed copy. The widget's Open command opens the installed copy. LaunchServices therefore resolves the bundle identifier (notification clicks, `open -b`) to the installed app only. The widget itself stays in `.runtime/`. A Dock pin or login item made before the install still points at `.runtime/AIREMonitorApp.app`; replace it with the installed app.
- **Removing.** `--uninstall` first cleans up leftover staging folders in the recorded folder (even when the record no longer names the app) and the default folders, putting back an install a killed run left in one. Before anything is asked to quit it checks that the account may delete every file in the bundle (access(2) with `_DELETE_OK` per entry, plus the file flags), so a locked bundle, an ACL or a read-only folder inside it stops it with nothing changed. It then applies the same quit rule and moves the bundle into a staging folder with `rename(2)`, which fails cleanly where the account may not move it. There it checks again that no copy started in the meantime and that everything can be deleted now that nothing runs from it; otherwise it puts the bundle back and opens the app again if it quit it. Only then does it unregister the bundle (while it still exists), remove the record, register the `.runtime/` bundle again and delete the staging folder. A run killed before that point leaves `previous.app` in the staging folder, which the next run puts back; after it, `removed.app`, which the next run deletes. After a move to another folder, the old install is removed the same way, and one that cannot be deleted completely is left whole (unregistered) with a warning.
- **Exit status.** 0 on success, 1 on an error, 2 for bad usage, 3 when a running copy did not quit, 75 when another install of the checkout held `.runtime/.install_app.lock` for over 1500 s (`HPC_INSTALL_LOCK_TIMEOUT`), and `build_bundle.sh`'s status when the build fails, including its own 75 when another build held its lock. The waiting script hands the locked one a marker file (`.runtime/.install_app.waiting.*`) that it deletes as soon as it starts, so only a 75 from the lock itself is reported as another install. `--installed-path` prints the recorded install and exits 0, or exits 1 when there is none; the other scripts use it, so it is answered before any other setting is checked. `HPC_LSREGISTER` replaces the `lsregister` tool (the tests use a stub).

Build system notes:

- **Configuration.** Release by default. `--debug` builds the debug configuration, which is several times slower on the main thread and carries the DEBUG-only preview hooks.
- **SDK.** An exported `SDKROOT` is respected; otherwise SwiftPM uses the SDK that `xcrun --show-sdk-path` reports. No SDK is pinned.
- **Parallelism.** SwiftPM's default. `HPC_BUILD_JOBS=<n>` passes `--jobs <n>`.
- **Build directory.** SwiftPM builds into the per-user Darwin temp directory (`$(getconf DARWIN_USER_TEMP_DIR)aire-monitor-build`, mode 700) rather than the project volume, because backup and sync tools that watch the project break llbuild's SQLite database mid-build. The name predates the rename and was kept so incremental state is reused. `HPC_SWIFTPM_BUILD_DIR` (or the older `AIRE_SWIFTPM_BUILD_DIR`) overrides it.
- **Build-error tolerance.** Some toolchain and macOS combinations fail the final `build.db` write-back ("disk I/O error") after a successful compile. Such a build is accepted only when SwiftPM reported completion **and** every executable is current: linked during this build, or none of its inputs changed since it was linked.
- **Logs.** `.runtime/swift-build.log` (`run_macos_app.sh`) or `.runtime/swift-widget-build.log` (widget alone); `HPC_BUILD_LOG` overrides. Each run truncates its log. A failed build ends the log with the deduplicated compiler errors and a final `build_bundle.sh: error: ...` line.
- **One build per checkout.** A `lockf` lock on `.runtime/.build_bundle.lock` makes a second launcher (a double-clicked Widget button, or `run_macos_app.sh` while the widget builds) wait its turn. Exit status: swift's own on a build failure, 75 when another build held the lock for over 1200 s, 1 for any other error.
- **Replace only on change.** Each bundle carries a content stamp (`HPCBuildStamp`: executable, artwork, Info.plist fields, signing identity and the script itself). An unchanged bundle is neither rebuilt nor restarted, and `--open` only brings it forward. A changed bundle is assembled in a staging directory, signed and verified, then swapped in; any instance running from it is stopped (SIGTERM, SIGKILL after 5 s) and relaunched on the new build. So a source change restarts a running app (closing its terminals), while a docs-only commit does not. The app's bundle is the exception once the app is installed, or with `--for-install` (see Installing above). There a running copy is left for `install_app.sh` to ask to quit.
- `.runtime/` is created with mode 0700 when it does not exist.

**Signing.** Bundles are signed with `codesign --force --sign <identity> --identifier <bundle id>`, with Info.plist bound and resources sealed. The identity is `HPC_CODESIGN_IDENTITY` (a name or SHA-1; `-` forces ad hoc), else a login-keychain certificate named `Leeds HPC Monitor Local`, else ad hoc. An ad-hoc signature changes with every rebuild, so Keychain asks again for the saved password after each one. A stable self-signed certificate stops that:

1. Keychain Access > Certificate Assistant > Create a Certificate...
2. Name `Leeds HPC Monitor Local`, Identity Type `Self Signed Root`, Certificate Type `Code Signing`.

The script finds the certificate by name, so it also applies when the app or the widget runs the launcher (GUI processes never see variables exported in a shell profile). If signing with that implicitly found certificate fails (a locked keychain, say), the bundle is signed ad hoc and marked for replacement on the next build.

**Info.plist provenance.** `HPCSourceRevision` (`git describe --tags --always --dirty`), `HPCBuildConfiguration` and `HPCBuildStamp` (per bundle, so not comparable between the app and the widget); read them with `defaults read <bundle>/Contents/Info HPCSourceRevision`. `CFBundleShortVersionString` is the newest `vX.Y.Z` tag, or `0.2.0`; `CFBundleVersion` is the commit count. Commit-only changes do not repackage a bundle, so these fields describe the build that last changed it. `LSEnvironment.HPC_PROJECT_ROOT` and `HPCProjectRoot` record the checkout, so a bundle installed or moved out of `.runtime/` still finds it. LaunchServices applies `LSEnvironment` only to launches it performs. `HPCProjectRoot` is read from the bundle itself, so it also works when the executable is started directly.

The raw SwiftPM commands are useful for debugging. Pass a scratch path outside the project, because the default `.build/` on the project volume can hit the `build.db` error above:

```bash
swift build --disable-sandbox -c release --scratch-path "$(getconf DARWIN_USER_TEMP_DIR)aire-monitor-build" --product AIREMonitorApp
swift build --disable-sandbox -c release --scratch-path "$(getconf DARWIN_USER_TEMP_DIR)aire-monitor-build" --product AIREDesktopWidget
```

Running the bare binary (`swift run`) works, but local notifications are disabled outside an app bundle, because `UNUserNotificationCenter` requires a bundle identifier.

This repository is built with the Command Line Tools only, not full Xcode. A true macOS WidgetKit extension requires an Xcode app target and an extension target, so the widget is a local desktop companion app rather than a system Notification Center widget.

## Project-Root Resolution

The app needs the repository checkout to find the `scripts/hpc_*` helpers and to keep its runtime state under `.runtime/`, also when it is installed in `/Applications`. It takes the first of these that contains `scripts/hpc_snapshot.py` (`ProjectRootLocator` in HPCCore):

1. the `HPC_PROJECT_ROOT` environment variable (set by the bundles' `LSEnvironment` when LaunchServices starts them), then the pre-rename `AIRE_PROJECT_ROOT`
2. the bundle's `HPCProjectRoot` Info.plist key, which `build_bundle.sh` sets to the checkout. It is read through `Bundle.main`, so it works for an installed copy whether LaunchServices started it or the binary was started directly
3. the current working directory
4. the grandparent directory of the app bundle, so the bundles under `.runtime/` are self-locating
5. the root last set by hand (UserDefaults key `projectRoot`), so a manual fix survives a relaunch exactly when auto-detection fails

The sidebar's Advanced section has a `Project root` field. An edit is validated and applied after a pause in typing, or at once on Return, and the field is locked during sign-in, so sessions only ever see a validated root, never a half-typed path. A new root moves every session's cache and widget lease and saves the preferences there. A root without the collector shows an explicit error. The widget resolves the checkout with the same `ProjectRootLocator` (steps 1–4); when none fits it shows a dedicated card and runs nothing.

## Architecture

```text
HPCCore (Foundation-only library, linked by the app, the widget and the tests)

AppModel (coordinator, one per app: AppEnvironment.model)
│  username · route · jump host · Duo option · Keychain item · login chain · preferences.json · lease heartbeat
│
├── ClusterSession "aire"     MonitorService ─ scripts/hpc_* ─ ~/.ssh/ctl/aire-<hash>.sock
│     refresh loop · cache writer · history · app_state.json · job notifications · GPU alert
│     TerminalManager · FileBrowserModel · ClusterDashboardState
│
├── ClusterSession "calder"   MonitorService ─ scripts/hpc_* ─ ~/.ssh/ctl/calder-<hash>.sock
│     (same, fully independent)
│
└── rash route only: ~/.ssh/ctl/jump-<hash>.sock, shared by every cluster's tunnel

Views: ContentView (sidebar + Overview or one ClusterDashboardView)
       StatusBarMonitorController + MenuBarMonitorView (menu bar)
Separate process: AIREDesktopWidget (reads .runtime/clusters/*/ and the enabled flags in .runtime/preferences.json)
```

### HPCCore

One implementation of every rule the surfaces must agree on, so the app, the menu bar and the widget can never disagree about what an idle GPU or an available node is.

### Cluster profiles and the catalog

`ClusterProfile.swift` holds everything the app knows about a cluster. `ClusterID` (HPCCore) is a string-backed identifier, not an enum, so generic code never switches on a particular cluster. Each `ClusterProfile` carries:

| Field | AIRE | Calder |
|---|---|---|
| `identity` (HPCCore `ClusterIdentity`: id, display name, monogram, accent) | `aire` / AIRE / A / green | `calder` / Calder / C / violet |
| `defaultHostname` | `aire.leeds.ac.uk` | `calder.leeds.ac.uk` |
| `partitions` (`PartitionHint`: name, role, summary, sort rank) | `gpu`, `nodes`, `himem`, `teachingnodes` | `calder-gpu-hopper`, `calder-cpu-turin`, plus the AIRE-generation `aire-gpu-lovelace` and `aire-cpu-genoa` on Calder's scheduler |
| `gpuPartition` (terminal "GPU nodes" chip) | `gpu` | `calder-gpu-hopper` |
| `storage` (`StorageVolumeSpec`, see the collector contract) | Home `$HOME` (nfs); Scratch `/scratch-aire/users/$USER`, `/mnt/scratch/$USER`, … (lustre); Flash `/flash-aire/users/$USER`, … (lustre, optional) | Home `$HOME` (nfs); Scratch `/scratch-calder/users/$USER`, … (lustre); Flash `/flash-calder/users/$USER`, … (lustre, optional) |
| `tagline`, `documentationURL` | header text, arcdocs AIRE pages | header text, arcdocs Calder pages |

`ClusterCatalog.all` lists the profiles in display order, which the sidebar, overview, menu bar and widget all use. A partition that no hint knows is still styled from its data: gres with a GPU gives it the GPU role, anything else the CPU role. `StorageKind` (home / scratch / flash / other) is derived from a volume's label, not its path, and drives icons, trend series and sort order; its colours mark identity only and never reuse a status colour. Only `home` is `isSharedAcrossClusters`: `/users` is one NFS export, so the overview and menu bar show its quota once and never sum it. `gpuModelDisplayName` turns a gres type into a label (`l40s` becomes `L40S`, `nvidia_h200` becomes `H200`).

**Adding a cluster:**

1. In HPCCore `Catalog.swift`, add a `ClusterIdentity` to `ClusterIdentity.known` (plus a `ClusterID` constant if wanted). Pick a short, stable, lowercase id (a letter, then letters, digits, `-` or `_`, at most 32 characters; the widget ignores any other directory name), because it becomes the `.runtime/clusters/<id>/` directory and the socket prefix. The widget takes the name, monogram, accent and order from here; a cluster missing there still appears, named from its snapshot, with a grey accent, after the known ones.
2. In `ClusterProfile.swift`, add a `ClusterProfile` with that identity and append it to `ClusterCatalog.all`. The catalog tests require distinct names, hosts, accents and monograms, a `gpuPartition` that is one of the profile's GPU partition hints, and an NFS Home (`$HOME`, not optional) as the first storage volume.
3. Add the cluster to the collector's `KNOWN_CLUSTER_NAMES` and `KNOWN_CLUSTER_HOSTNAMES` (used only for manual command-line runs; the app always passes both) and regenerate the fixtures with `python3 scripts/tests/test_snapshot.py --write-fixture`. `CollectorContractTests` fail while that table and `ClusterIdentity.known` disagree.

Nothing else is cluster-specific. `AppModel` creates one `ClusterSession` per catalog entry, and a new cluster starts enabled. Preferences, control sockets, the runtime directory, collector arguments, notifications, terminals, files and the widget all key off the id. Two assumptions are built in: the rash route assumes the same username is valid on the jump host and on every cluster, and the overview, menu bar and file manager assume every catalogued cluster mounts the shared `/users` home.

### ClusterSession: one cluster's lifecycle

`ClusterSession` (`@MainActor`, one per cluster) owns everything about one cluster: `isEnabled`, its login `hostname` (blank falls back to the profile default), sign-in and refresh flags, `snapshot`, `history`, pause state, the current refresh interval, plus `dashboard` (`ClusterDashboardState`: selected tab, job sheet, filters and detail toggles, so switching clusters restores exactly where the user was), `terminals` (`TerminalManager`) and `files` (`FileBrowserModel`). Sessions share nothing mutable. A failing, paused or disabled Calder never affects AIRE.

`settings` (`ConnectionSettings`) combines the shared sign-in configuration with the profile: cluster id and name, username, host, route, jump host (blank means `rash.leeds.ac.uk`), Duo option (blank means `1`), project root and storage spec, and derives the runtime directory and both control-socket paths. While signed in, `settings` is the identity the session was established under (`activeConnection`); `configuredSettings` is what the form says. Refreshes, terminals, file operations and Cancel job use the former, so typing in the sign-in form or a host field never re-targets a live session. The sidebar then says "Changes apply at the next sign-in to …", and a sign-in under a different identity retires the previous identity's master only once it has succeeded (see Sign-in side effects).

Two derived views collapse the flags. `connectionState` (first match wins: `disabled`, `connecting`, `queued`, `paused`, `live`, `cached`, `notConnected`) serves the coarse pills. `presentation` (`ClusterPresentation`) is the shared wording for the hero, sidebar row, overview card, status pill and menu bar: phases `off`, `notConnected`, `checking`, `queued`, `signingIn`, `loadingFirstSnapshot`, `live`, `paused`, `stale`, at most one primary action (`connect`, `turnOn`, `resume`), and `allowsRefresh`. `checking` means the startup or route probe is still running: no surface offers Connect then, and Connect all skips the cluster, because the probe may be about to confirm a live master.

**Startup.** `start()` loads the cluster's cached snapshot, history and job baseline, and writes `app_state.json` at once, replacing a paused or off record a previous run left behind. If the cluster is enabled, it starts the background timer and runs one probe refresh. If a ControlMaster from an earlier run is still alive (within its 24 h idle limit), the cluster goes live without a sign-in and the master is adopted (below). Otherwise it stays cached or not connected.

**Adoption.** When a session goes live without having signed in during this run (startup or route probe, or recovery), it runs `hpc_start_target_master.zsh` once per control path in the background, with `HPC_REUSE_ONLY=1`, an empty closed stdin and a 40 s limit. The starter verifies the master and ends what older releases left beside it (a 5 s keepalive and a permanent remote `sleep` session), so ControlPersist can finally idle out. Exit 0 means adopted and exit 4 means nothing to adopt; either way, and on any other result, the outcome is only logged (category `login`). Adoption never prompts, pushes Duo or tears anything down. A master built by a sign-in counts as adopted, and a pending adoption is cancelled by a sign-in (which waits for it), a route change, Disconnect and quit.

**Refresh loop and classification.** The timer fires every 10 seconds and each refresh runs the collector through `MonitorService.collectSnapshot`. `RefreshClassification` (`FoundationRefreshRules.swift`) judges the result:

- **success**: `errors` is empty. `warnings` (enrichment problems) are shown but never mark the cluster offline.
- **scheduler error**: errors, but the collector's `remote` section answered, so Slurm failed over a healthy master. The session stays live, failed core sections keep their previous data (the collector's errors move to warnings, with a "showing the previous …" note; a "No usable jobs listing" error counts as a failed `jobs` section, so the previous job list stays), and `schedulerIssue` names the problem. It backs off but never counts toward the logout.
- **transport**: errors with no remote answer, or the collector threw (missing master, refused session, network, its 40 s watchdog).
- **configuration**: the collector could not start (script missing, runtime folder not creatable, no `python3`). Signing in cannot fix it, so the connection state is left alone.

On success the session merges storage (below), writes `latest_snapshot.json`, appends one line to `snapshot_history.jsonl` (deduplicated by collection time; the newest 1440 points, about 4 h, are kept and the log is compacted once it is 360 lines over), rewrites `collector.json` when the collector argv changed, processes job notifications and the GPU alert, and resets the failure counter and interval. On any failure the interval backs off exponentially (10, 20, 40 s, capped at 60 s), the last good snapshot stays on screen, and failed data never overwrites the cache. Three **transport** failures in a row drop the session to "not live"; a refused extra session (sshd's MaxSessions) proves the master alive and does not count. Every attempt rewrites `app_state.json`. Cache writes run on a serial background queue (`ClusterCacheWriter`), and a write that fails three times in a row is reported once as an app-level error.

**Refresh failures.** `lastRefreshFailure` (`RefreshFailure`: kind `configuration` / `clusterSide` / `transport`, a one-line message capped at 160 characters, the full detail, the consecutive count and the date) is set on every failed refresh, startup probes and automatic ones included, and cleared on success, sign-in, route change, Disconnect and switching monitoring off or on. Typical messages: "Collector script missing at <path>", "No <cluster> SSH session — sign in to refresh", "<cluster> refused another SSH session", "Slurm error on <cluster>: …", or the error's first line. For a configuration error `statusMessage` is the message itself. `errorMessage` stays reserved for things the user did (sign-in, a manual Refresh, Cancel job). The dashboard's status strip renders the failure (see [Current Views](#current-views)).

**Missing-master detection.** If the failure says the ControlMaster is gone, the session marks itself not live immediately instead of "offline, retrying", and the status line asks for a sign-in. Two messages count as gone: the collector's local `ssh -O check` probe ("control master is not running") and `MonitorService.requireLiveMaster` ("SSH session expired"). The backoff timer keeps running, so a master that comes back is picked up. The exception is a deliberate Disconnect: the timer then stops and the "Signed out …" line stays. Refresh still probes, and finding no master there is not a failure (the signed-out line is put back); a master that turns up (started from a terminal, say) makes the session live again and restarts the timer. A probe that merely timed out is not treated as missing, because a wedged master may recover.

**Storage cadence.** Most refreshes pass `--skip-storage`. Storage is collected on the first refresh after start or sign-in, on a manual Refresh, while the Storage tab is open, and once the last collected rows are 300 s old. When a requested storage section comes back missing (the collector's stuck-storage guard, or the budget ran out) or with rows cut short (`not-collected`, or `no-figures` from a stalled `df`/`lfs`), that is a miss, not a collection: automatic refreshes wait 60 s before asking again. A row cut short keeps its label's previous figures for up to 600 s after the last complete collection (`storageCarryLimit`), with `storageCollectedAt` left at the older time; after that a volume that keeps failing shows as unreadable. `storage: null` keeps the previous rows (`storageCollectedAt` records when they were collected); `[]` means collected, no volumes. The rows, their carry-over and the miss wait belong to the account that collected them: when a refresh runs under another username than the rows on screen (after a sign-in, or a master found, under another account), they are dropped before the merge, so the previous account's usage and resolved paths are never kept or carried as this one's. The job list goes with them (it is per account too), so a Slurm-error refresh whose jobs section failed shows no jobs rather than the previous account's queue; partitions and nodes are cluster-wide and stay. Storage then shows a gap until the new account's first complete collection (the next refresh asks for one if this one did not). A login-host change alone keeps the rows. History points are taken from the merged snapshot, so skipped refreshes carry the last figures forward. A cut-short optional volume (`unavailable` / `not-collected`) is shown only if that label has had real figures, so AIRE's absent Flash stays hidden. `collector.json` never contains `--skip-storage`, because the widget replays it verbatim.

**Refresh generations.** Every refresh carries a generation number. A sign-in, pause, route change or disabling the cluster bumps it and cancels the in-flight refresh, so a late completion cannot repaint state or restart the timer; a sign-in also waits for the cancelled refresh to exit before it touches the ControlMaster. Background ticks run silently (`refreshInFlight`); `isRefreshing` is set only for refreshes the user should see (probe, post-login, manual). A manual Refresh on a cluster with no known master, or still checking, probes quietly instead of painting an error. `refreshAfterMutation()` (after `scancel`) is never dropped: if a refresh or sign-in is running, a pending flag starts one follow-up refresh when it completes.

**Pause.** Pausing is per cluster. It stops the timer and invalidates any in-flight refresh. A manual Refresh still runs once while paused, Resume refreshes immediately and restarts the timer, and signing in always clears the pause. The pause is written to `app_state.json`, so the widget never collects a paused cluster, even after the app quits (see [Desktop Widget Data Flow](#desktop-widget-data-flow)). A **disabled** cluster never refreshes, takes no part in Connect all, and keeps its cache on disk; the overview hides its cached data and the widget stops showing it.

**Route changes.** When the route flips (after a confirmation if that ends a live session, a running terminal or an active transfer; see [AppModel](#appmodel-the-coordinator)), every enabled session closes its previous route's master (through `hpc_stop_master.zsh`, never touching the jump master), drops its live state and probes the new route's socket. Each route has its own socket, so a master that is already alive under the new route reconnects instantly; otherwise the user signs in.

**Sign-in side effects.** A successful sign-in records `collector.json`, asks the file browser to drop any folder listing that belonged to a different account or login host (`files.reconcileConnectionIdentity()`; a route change does the same), and starts one refresh that also collects storage. A sign-in under a different identity (account, host or route) then closes the previous identity's master; a failed, cancelled or Duo-less one closes nothing. While any terminal of the cluster runs or any file transfer is waiting or running, a plain sign-in keeps that master (the session does not track which master each rides on, and a transfer keeps the settings it was queued under) and closes it after the first successful refresh with neither, at a later successful sign-in that finds neither, or with Disconnect; the confirmed Reconnect closes it at once, as its dialog said. A refresh that finds a master under another identity than the one last live retires the earlier master the same way. The master the session is live on is never retired.

**Disconnect.** `ClusterSession.disconnect(stopJumpIfUnused:)` cancels a running or queued sign-in instead, if there is one. Otherwise it stops the timer (see Missing-master detection), invalidates the refresh and any adoption, closes any earlier identity's master kept for its terminals or transfers, then closes the master with `MonitorService.stopMaster` (`hpc_stop_master.zsh` with a 30 s limit and stdin `/dev/null`, or `ssh -O exit` when the script is missing) and keeps the last snapshot as cached data. On the rash route, when no other enabled cluster is live, signing in or queued on the same jump socket, `AppModel` passes `HPC_STOP_JUMP_IF_UNUSED=1`. The script still keeps the jump master if anything rides on it, and the status line says so calmly ("Signed out — showing the last snapshot • rash.leeds.ac.uk stays signed in for another connection"). Only a failed Disconnect (exit 1: a verified master survived SIGKILL) is shown as an error; stops caused by a route or identity change are only logged.

**Job notifications.** Each cluster keeps its own job-state baseline (`job_state.json`), because Slurm job IDs are only unique within one controller. It is keyed on the account (`user@<cluster>`), not the login host: `squeue -u` answers the same from every login node, so changing only the host keeps diffing, and a baseline an earlier build keyed on `user@host` still matches its account. `JobStateDiff` compares it with each successful refresh's jobs: a job going from pending to running is a start, and a terminal state (`COMPLETED`, `FAILED`, `CANCELLED`, `TIMEOUT`, `OUT_OF_MEMORY`, `NODE_FAIL`, `PREEMPTED`, …) or leaving `squeue` is an ending. For arrays, a task that starts out of a pending remainder counts as started, and a remainder that vanishes while tasks remain is not an ending. The baseline advances after every successful refresh, whether or not notifications are allowed, and is rewritten when states change and at least once a minute. The gap since the baseline decides delivery: up to 10 minutes gives individual alerts ("Calder · job started", "Calder · job ended", several endings in one refresh as one "jobs ended" summary); up to 24 hours gives one catch-up alert ("Calder · while you were away"); anything older, an unreadable baseline, or one recorded for another account, is re-seeded silently. Alerts are threaded per cluster and need an app bundle and notification permission.

**GPU-free alert.** `notifyWhenGPUFrees` is one global, opt-in preference (UserDefaults, off by default). When it is on, each cluster watches its own startable idle GPUs (idle GPUs on an available node with a free CPU) and notifies on a 0 → >0 transition, naming the GPU models and partitions. Unknown allocation suspends the check. Each cluster has its own 10-minute cooldown; a transition suppressed by the cooldown keeps the baseline at zero, so it fires once the cooldown expires. The baseline lives in memory only.

**Cancel job.** `cancelJob` runs `scancel '<jobid>'` over this cluster's ControlMaster (`MonitorService.runRemoteCommand`, 30 s). For the pending remainder of an array it runs `scancel --state=PENDING '<array id>'`, so tasks already running are untouched. A timeout says "scancel did not answer in time; the next refresh shows whether the job was cancelled." Either way it then calls `refreshAfterMutation()`.

### AppModel: the coordinator

`AppModel` (`@MainActor`, the single instance `AppEnvironment.model`) owns the shared sign-in state: `username`, a transient `password` field (never persisted, cleared after a successful sign-in), `connectionRoute`, `jumpHostname`, `duoOption`, `rememberPassword`, `projectRoot` and the sidebar `selection` (`.overview` or `.cluster(id)`). It also owns dismissable app-level errors, the notification-permission summary and its button action, the GPU-alert preference and `isPreparingDesktopWidget`. Construction has no side effects; `start()`, called from `applicationDidFinishLaunching`, begins monitoring. It forwards every session's `objectWillChange`, so views that observe only the coordinator, like the menu bar and the overview, repaint when any cluster changes.

**Plain sign-in and forced replace.**

| Call | Used by | Effect |
|---|---|---|
| `signIn(ids)` | sidebar Connect / Connect all, Return in the password field, and the Connect buttons on sidebar rows, overview cards, the hero and the status strip (through `signInOrConfirm`) | `HPC_FORCE_RELOGIN=0`: a healthy master is reused, with no teardown and no Duo push, and terminals survive; an unresponsive one is left running (exit 5) |
| `connect(id)` | menu bar Connect | the same plain sign-in |
| `connectAll()` | no button (API and tests) | plain sign-in for enabled clusters that are not live, signing in, queued or `checking` |
| `reconnect(ids)` | only `perform(.reconnect)`, after the confirmation dialog | `HPC_FORCE_RELOGIN=1`: replaces each master, one Duo push per cluster, open terminals there close |

Connect on a cluster that is already live becomes the confirmed Reconnect. "Reconnect…" (in the dashboard ⋯ menu, the sidebar session panel and the sidebar Reconnect… menu) always asks; the dialog names the Duo cost (plus one push for rash if its session has closed), warns that the old session closes first, so a missed or declined push leaves the cluster signed out (whenever there is a session or running work to lose), and says how many running terminals close and how many file transfers stop. Disconnect asks only when terminals are running or file transfers are waiting or running; when it would also close the shared rash jump master, the dialog says so and that signing back in takes two Duo approvals. The route picker switches at once only when that ends nothing; otherwise it asks, naming the sessions that close, their terminals and their transfers (`changeRouteOrConfirm`).

**Login chain.** Before anything is queued, `enqueueLogins` validates the username, the jump host (rash route only), and the password: the typed one, or the saved one when the field is empty, Remember is on and the saved password has not been flagged as rejected. It marks every candidate as queued and appends one `Task` to `loginChain` that awaits the previous link. This serializes sign-ins across calls, so Duo pushes arrive one at a time and two clusters never race to build the shared rash jump master. A saved password is read off the main actor; a denied Keychain prompt abandons the queue with a message. Each queued sign-in uses the configuration captured when it was queued. Outcomes:

- `succeeded`: save the password if needed (only when a server checked it; see Keychain), and clear the field.
- `passwordRejected` (exit 13), `passwordExpired` (14), `jumpHostFailed` (any other rash-leg failure) and `duoNotApproved` (15): cancel every queued sign-in with a "Skipped — …" reason and stop. Sending the same wrong password to the next cluster would only push the account towards a lockout, and nobody is answering the pushes. A saved password that was rejected or expired is flagged (UserDefaults, per account) and not sent again until a typed password that a server accepted is saved over it, or it is forgotten. A Duo failure never flags it, because the password was accepted.
- `timedOut` (124) or `cancelled`: skip the clusters still queued by the same call; those a separate Connect queued are their own link and go ahead.
- `failed` or `skipped`: continue with the next cluster.

**Cancel.** `cancelLogins()` (the sidebar's primary button while signing in, and at quit) stops every link of the chain. A cluster's own Cancel (`ClusterSession.cancelLogin()`, on its banner, the status strip, the overview card and the hero) drops a queued sign-in, or cancels the running one, which also skips the clusters queued by the same call (its tooltip says so and points to the sidebar's Cancel sign-in) and sends SIGTERM to the helper's process group at once, so a late Duo approval cannot build a master. A cancelled sign-in is followed by a quiet probe, because a forced sign-in may already have closed the old master.

**Keychain.** There is one item for the university account: service `AIREMonitor.AIREPassword`, account `leeds:<username>`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. Accounts written by single-cluster releases are read as a fallback: `explicit:<user>@<host>:direct` and `explicit:<user>@<host>:via:<jump>` for each cluster's current host, and the original `<user>@leeds`. Only after a sign-in in which a server actually checked the password (some leg printed `HPC-STATUS: password sent (…)`; `LoginResult.passwordVerified`), and with Remember enabled, is it saved under `leeds:<user>`, when it was typed or when nothing is stored there yet; the legacy entries are then deleted, and a typed password lifts the rejected flag. A sign-in that only reused open sessions never saves a typed password. `Forget` deletes both. Unticking Remember with a password saved asks whether to remove it too. Keychain access never runs on the main actor, and existence checks are debounced by 300 ms on username and jump-host edits.

**Preferences.** The password-free `.runtime/preferences.json` stores username, route, jump host, Duo option, `rememberInKeychain`, sidebar selection, and each cluster's `enabled` flag and `hostname`, written 500 ms after the last change. The password is never persisted; the project root lives in UserDefaults only.

**Locks.** The route picker, username, Duo option, cluster toggles and hosts, jump host and project root are locked while any sign-in is queued or running, so nothing can repoint an in-flight ControlMaster or change the account a resolved password is sent to.

**Lease heartbeat.** Every 30 s each session rewrites its `app_state.json`, because paused and switched-off clusters never refresh and their lease would otherwise expire.

**Desktop widget.** `openDesktopWidget()` always runs `scripts/run_desktop_widget.sh` (via `/bin/bash`, with the scrubbed child environment plus `HPC_PROJECT_ROOT`, stdin `/dev/null`). Its output goes to `.runtime/widget-launcher.log`: a file rather than a pipe, because the script may start the widget binary directly, which inherits those descriptors. When the bundle is current, the script only brings the widget forward. While it runs, the sidebar's Widget button shows progress and further clicks (from either Widget button) are ignored. A non-zero exit shows the last 5 lines of `.runtime/swift-widget-build.log` (if this run wrote it) or of the launcher output; exit 75 says another build is running and to try again once it has finished.

### App lifecycle

- **One instance per user.** Before any session exists, `SingleInstanceGuard` takes an `flock` on `~/Library/Application Support/LeedsHPCMonitor/app.lock`. A second copy activates the running one and exits. The lock is per user, not per checkout, because masters and sockets are per user.
- **Quit prompt.** `applicationShouldTerminate` asks once (`QuitConfirmation`) when terminals are running, file transfers are unfinished (quitting cancels them and removes partial files), or a sign-in is in progress.
- **Termination.** `prepareForTermination()` cancels sign-ins, stops the heartbeat, flushes each session's job baseline and history, and saves preferences. `app_state.json` is deleted for enabled, unpaused clusters, so the widget can take over at once; paused and switched-off clusters keep a final record (`live: false`).
- **Go menu.** ⌘0 overview, ⌘1…⌘9 clusters in sidebar order, ⌥⌘1…⌥⌘7 the selected cluster's tabs, ⌘[ back to the overview. ⌘R refreshes the visible cluster (or every cluster on the overview).

## Connection Architecture

The app uses the local system `ssh` and `expect`. It installs nothing on the clusters and never writes remote files on its own: the interactive Terminal and the Files tab run what the user types or clicks. Login is performed by helper scripts that the app drives as child processes. The password is written to each helper as the **first line of stdin**, and never appears in any argv or child environment. Every child process (helpers, collector, remote commands, scp, `-O check`, the stop helper, terminals, the widget launcher) gets the app's environment minus `HPC_PASSWORD`, `HPC_ASKPASS_PASSWORD`, `AIRE_PASSWORD` and `AIRE_ASKPASS_PASSWORD` (`MonitorService.childEnvironment`), and a child that needs no input gets `/dev/null`, never the app's own stdin.

### Routes

The sidebar offers exactly two routes, which apply to every cluster. **Both are explicit and username-based.** The app generates the ssh options from its own fields and manages its own ControlMaster sockets under `~/.ssh/ctl/`. It never uses a `~/.ssh/config` alias; the collector keeps a `--host <alias>` mode purely for manual command-line testing.

- **Direct (VPN)** (`directVPN`) connects straight to each cluster's login host over the University VPN or campus network. Each cluster needs one Duo approval.
- **Via rash jump host** (`rashJump`) tunnels through `rash.leeds.ac.uk`, so it works off-VPN. It needs one Duo approval for rash, which every cluster shares and which is reused while healthy, plus one per cluster.

### Login sequence

`MonitorService.login(settings:password:forceReplace:renewJumpHost:onStatus:)` signs in to one cluster:

1. **Jump leg (rash route only).** `scripts/hpc_ssh_login.expect` runs with the password on stdin and `HPC_SKIP_TARGET=1`, so it only makes sure the shared jump master is up (see the [shared jump master policy](#shared-jump-master-policy)) and exits. It reads stdin first and falls back to `HPC_PASSWORD` only when stdin is empty. The app attributes this leg's failures to "rash.leeds.ac.uk (jump host)", not to the cluster: exit 13 means rash rejected the password, exit 15 that the rash Duo push was not approved. On the direct route this step is skipped.
2. **Target leg (both routes).** `scripts/hpc_start_target_master.zsh` runs, again with the password as the first stdin line (read with `IFS= read -rs`; `HPC_PASSWORD` only when stdin is empty, and every password variable, including the pre-rename `AIRE_*` names, is scrubbed at once).
   - **Reuse unless forced.** Without `HPC_FORCE_RELOGIN=1`, a healthy master (`ssh -O check` plus a read-only `auth_ok|host|user|date` command through it within 15 s) is reused: "reusing the existing <X> session", then "connected to <X>", with no password needed, no teardown and no Duo. A master that answers `-O check` but not the 15 s `auth_ok` check may be wedged, or merely slow while it still carries terminals, so a plain sign-in leaves it running and exits **5** (`MonitorError.existingSessionUnresponsive`: nothing closed, no password sent, and the user is pointed to Reconnect…; a dead link also closes itself within about five minutes). Only `HPC_FORCE_RELOGIN=1` (the confirmed Reconnect) replaces it. Every run first stops any keepalive an older release left for this control path.
   - When a new master is needed on the rash route, it checks the jump master with `ssh -O check` and exits **3** if it is not running. With a dead jump socket, the ProxyCommand would fall back to a direct connection to rash, and rash's "Permission denied" must not be mistaken for a rejected cluster password.
   - **Teardown** (replacement only): `ssh -O exit`, socket removal, then a verified SIGTERM of this control path's master processes (from the per-path pid file `master-<socket name>.pid`, the shared `master_ssh.pid` of older releases, and a pattern search), waiting about 3 s and sending SIGKILL to any that still verify, so a dying master cannot unlink the replacement's socket. The kill rules live in `scripts/hpc_ssh_common.zsh`: a process qualifies only if it is an `ssh` whose *first* `ControlPath=` option is exactly this socket and that carries `ControlMaster=yes`, or if it is titled `ssh: <socket> [mux]`. The jump master, other clusters' masters and every cluster's `-W` proxy therefore never match. Masters started with `-N` (all the scripts' masters) keep their argv as their `ps` title, because OpenSSH then skips `control_persist_detach()`, which sets the `[mux]` title; that title appears only on masters older releases started with a remote command.
   - **The master** is a detached `ssh -f -N` with the shared option set (`hpc_master_login_options`: password and keyboard-interactive only, `NumberOfPasswordPrompts=1`, no public-key or GSSAPI, `ServerAliveInterval=30` × 10, `ConnectTimeout=20`, `ControlMaster=yes`, `ControlPersist=24h`) plus `Compression=yes`. With `-N` the master holds no session of its own, so `ControlPersist=24h` is an **idle** limit: the master closes 24 h after its last client (collector, the widget's fallback collection, a terminal, a transfer) went away. On the direct route it uses `ProxyCommand=none` and `ProxyJump=none`, so a `~/.ssh/config` entry cannot reroute it. On the rash route it uses `ProxyCommand=ssh -o BatchMode=yes -o PubkeyAuthentication=no -o GSSAPIAuthentication=no -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no -o ConnectTimeout=20 -o ControlMaster=no -o ControlPath=<jump socket> -o User=<user> -W %h:%p <jump host>`: a pure client of the jump master whose fallback dial to rash fails at once.
   - **Askpass.** `SSH_ASKPASS` (`scripts/hpc_ssh_askpass.sh`) answers the prompts. The password reaches it through a **0600 FIFO** in the cluster's 0700 runtime directory, served exactly once (AIRE and Calder offer only keyboard-interactive, so a login has a single password prompt; a second prompt finds no FIFO and is refused, so a wrong password is never sent twice). The writer exits as soon as ssh returns or the starter dies. The password is never put in ssh's environment, because `ssh -f` daemonizes into the long-lived master with that environment intact. Askpass answers the Duo prompt once with `HPC_ASKPASS_DUO_OPTION`; a repeated Duo prompt (push declined or timed out) makes it end the authenticating ssh, so one login sends one push. Password-change and unknown prompts are refused. Askpass records fixed words in `askpass.events` (`password`, `password-retry`, `password-change`, `duo`, `duo-denied`, `duo-timeout`, `duo-retry`), which the starter turns into progress lines and exit codes; "waiting for Duo approval" is printed only after a real Duo prompt.
   - **Deadline and verification.** `HPC_TIMEOUT` bounds connect, password and Duo together. After authentication the starter polls the socket (`-O check`, then the `auth_ok` command) for up to `HPC_VERIFY_TIMEOUT` (90 s) and records the master's pid.

There is no keepalive: nothing exercises, supervises or restarts a master, so a dead one can never turn into a reconnect loop.

Each leg runs under a 240-second process watchdog (`HPCDefaults.loginWatchdog`, `HPC_TIMEOUT` plus 60 s), a backstop for a hung helper. The combined stdout and stderr of both legs is appended to the cluster's `login_debug.log`, and the expect helper writes its own event log to the same file. After sign-in, refreshes, terminals, file operations and `scancel` all multiplex over the cluster's socket and can never prompt. Their client options come from `SSHMuxOptions`: `-S` (or `-o ControlPath=` for scp), `User`, `BatchMode=yes`, `PasswordAuthentication=no`, `KbdInteractiveAuthentication=no`, `ConnectTimeout=5` and `ControlMaster=no`. `runRemoteCommand` and `runTransfer` first run `requireLiveMaster` (`ssh -O check`, 5 s), because a dead master makes OpenSSH silently dial the host directly, bypassing the jump host.

Honoured by the scripts but not set by the app: `HPC_JUMP_PROBE_TIMEOUT` (jump health probe, default 10 s), `HPC_VERIFY_TIMEOUT` (default 90 s), `HPC_SSH_VERBOSE=1` (`-vv` in the master log) and `HPC_DEBUG=1` (redacted askpass prompt log).

### Shared jump master policy

On the rash route there is exactly one jump master per `user@jump-host`, and every cluster's target master tunnels through it. Closing it silently kills every cluster's tunnel. The expect helper therefore **reuses a healthy jump master and never tears one down because of `HPC_FORCE_RELOGIN`**. Forcing applies to the target only, and the target starter never touches the jump master. Re-signing in to AIRE does not drop Calder's tunnel, and vice versa.

A jump master counts as healthy when:

1. `ssh -O check` succeeds. This is an instant local probe of the control socket.
2. A bounded end-to-end probe succeeds. `ssh -o ControlPath=<jump> -W <cluster host>:22 <jump host>` waits up to `HPC_JUMP_PROBE_TIMEOUT` (10 s) for the far sshd's `SSH-` banner and then hangs up, so no authentication is attempted on the far side. `-O check` alone is not enough, because a master whose TCP connection silently died keeps answering its local socket (until ServerAlive gives up, up to 5 minutes) while every channel through it hangs.

Two refinements keep a responsive jump master when the problem is the cluster rather than rash:

- If rash relays a refusal ("Session open refused by peer"), or the channel opens and the far sshd hangs up before its banner (Calder's "Not allowed at this time"), rash demonstrably carried traffic. The master is kept once a second `ssh -O check` confirms it survived the probe, and the target leg then reports the real error.
- If the probe to the cluster times out, a second probe asks rash for its own sshd (`127.0.0.1:22`). Any answer keeps the master.

Only a jump master that is missing, fails at the mux layer, or carries no traffic at all is closed and re-authenticated, at the cost of one rash Duo push. Because `AppModel` serializes sign-ins, two clusters never race to build it. If the jump master dies (for example after a network change), every rash-route cluster's master dies with it, and the next sign-in re-authenticates rash once.

### Stopping a master

`scripts/hpc_stop_master.zsh` signs out of exactly one control path: `ssh -O exit` (local socket only, capped at 10 s); a verified SIGTERM, about 3 s wait and SIGKILL of that path's master processes (the same rules as the starter); any leftover keepalive for that path; then it removes `master-<socket name>.pid`, the shared pid files of older releases only when they cannot belong to another route, and a dead socket file. It prints "stopped the <X> session" or "no <X> session was running". With `HPC_STOP_JUMP_IF_UNUSED=1` it also closes the shared jump master, but only when no other process names its control path (another cluster's `-W` proxy, a sign-in, a collector). Counting those riders, it leaves out exactly the pid `-O check` reports as serving the socket (and a `[mux]`-titled master), since the jump master's own argv names the path just as a jump master still authenticating does; when the socket does not answer, nothing is left out, so anything naming the path keeps it. It prints "stopped the shared jump-host session (<jump host>)" or "kept the shared jump-host session (<jump host>): another connection still uses it". Exit 0 means stopped or nothing was running, 1 that a verified process survived SIGKILL, 2 a configuration error or refusal.

### The HPC-STATUS protocol

The helper scripts report milestones on stdout as machine-readable lines:

```text
HPC-STATUS: starting jump-host authentication
HPC-STATUS: password sent (jump host)
HPC-STATUS: waiting for Duo approval on your phone (jump host)
HPC-STATUS: jump host connected
HPC-STATUS: reusing the shared jump-host session
HPC-STATUS: jump host is up, but Calder did not answer through it yet
HPC-STATUS: jump host is up, but Calder is slow to answer through it
HPC-STATUS: reusing the existing Calder session
HPC-STATUS: starting Calder authentication
HPC-STATUS: password sent (Calder)
HPC-STATUS: waiting for Duo approval on your phone (Calder)
HPC-STATUS: verifying Calder connection
HPC-STATUS: connected to Calder
```

`MonitorService` streams child stdout line by line as it arrives, filters for the `HPC-STATUS: ` prefix (`MonitorService.statusLinePrefix`), and forwards each message to that session's `loginProgress`. The sidebar shows one progress banner per signing-in or queued cluster, each with its own Cancel, and the status strip and menu bar show the message under the cluster's name, so the user can tell which push to approve and can tell "your password was wrong" apart from "go approve the Duo push". The stop helper uses the same prefix.

### Exit codes and failure diagnosis

| Code | Meaning | In the app |
|---|---|---|
| 0 | connected (a new master, or a healthy one reused) | |
| 2 | configuration problem (missing variable, helper or password; a control path equal to the jump socket) | sign-in failed |
| 3 | target starter: the shared jump master was not running | sign-in failed; should not happen right after a successful jump leg unless rash dropped in between |
| 4 | `HPC_REUSE_ONLY=1` and no healthy master | nothing to adopt (logged only) |
| 5 | target starter, plain sign-in: a master answers `-O check` but not the 15 s check; it was left running | `existingSessionUnresponsive`: nothing closed, no password sent, "Reconnect… replaces it"; the queue continues |
| 13 | the password was sent and rejected (a second password prompt, or this cluster's "Permission denied" with no Duo exchange) | `passwordRejected`: "re-enter it, check for a pending lockout"; queue stops, saved password flagged |
| 14 | a password-change prompt (expired password), refused | `passwordExpired`; queue stops, saved password flagged |
| 15 | the password was accepted, then Duo was not approved (declined, timed out, or the connection dropped); no second push | `duoNotApproved`: "the Duo push was declined or timed out. Your password was accepted. Approve the push on your phone and connect again."; queue stops, saved password untouched |
| 124 | the helper's deadline passed before Duo, or the app's watchdog fired | `loginTimedOut`, worded as a login timeout; the remaining queued clusters are skipped |

Other failures are matched against common ssh output by `MonitorService.explainSSHFailure`, with the cluster's name in each message:

- A refused extra session on a healthy master (MaxSessions) asks to close some terminals or transfers.
- "Not allowed at this time", `kex_exchange_identification`, and connection closed or reset are explained as a server-side refusal, not a wrong password.
- "UNKNOWN port 65535" (a failed ProxyCommand) blames the rash tunnel.
- Banner-exchange timeouts get route advice.
- `Permission denied`, unresolvable hostnames, and a stray `ssh-askpass` each get a specific message.

A collector killed by its watchdog and a `scancel` that times out get their own messages, never the login-timeout wording. Every message includes the raw ssh output.

## Sessions: Sharing, Renewal and Drops

### Sharing with Terminal and Claude sessions

`SessionSharing.swift` lets every other program ride the app's sign-in. Another program might be `ssh`, `scp` or `rsync` in Terminal, or a Claude session running commands on a cluster. With **Share with Terminal and Claude sessions** on (the Sessions card; default on), `AppModel` runs a sharing pass whenever a session goes live or away, and every 30 s:

- **Stable links.** `~/.ssh/ctl/<name>.sock` points at each live master: `aire`, `calder`, and on the rash route `rash` (the jump master). `scripts/hpc-session` and `ssh -S` use these.
- **Alias links.** Every literal `Host` alias in `~/.ssh/config` (and the files it `Include`s) is resolved with `ssh -G <alias>`. That runs locally, never connects, and is cached until the config files change. An alias whose host, user and port 22 match a live master gets a symlink at its own `ControlPath` (`%C` and friends expanded by ssh). A plain `ssh aire` then multiplexes over the app's session: no password, no Duo. An alias with `ProxyJump rash` rides the shared rash session for its first hop as well.
- **Never over someone else's live session.** A path where another live master listens is reported as held by your own session and left alone. That covers your own `ssh aire-rash`, or a link you made yourself. It is linked once that master has gone. A dead socket left behind is replaced, as ssh itself would unlink it. Links are created with `symlink(2)` only, never renamed over a path, so a master ssh binds there at the same moment is never clobbered.
- **Cleaned up.** The links the app made are recorded with their targets in `~/.ssh/ctl/shared-sessions.json` (0600), which also lists every session's start time and each alias's state for the CLI. When a master goes away, or sharing is switched off, each recorded link that still points where the app put it is removed, so `ssh <alias>` can become a master of its own again. Links survive an app quit, like the masters.
- A Reconnect binds the same socket path, so links keep working without a pass; a route change moves them.

Passes run only once every enabled cluster's startup probe has answered, so a relaunch never removes links to masters that are fine. `scripts/hpc-session` (`status`, `check`, `wait`, `run <name> [--wait S] -- <command>`, `shell`) rides the stable links with `-F /dev/null`, `BatchMode` and `ProxyCommand=false`. It never prompts and never dials directly, and it exits 75 when a session is down or dropped mid-command.

### Session ages and Renew all

A master's age is its socket's birth time (`st_birthtime`). That is the moment the sign-in completed, for masters adopted from an earlier run too. The Sessions card shows each age (rash, AIRE, Calder), and so do the menu bar dropdown and `hpc-session status`. An age of 11 h or more turns orange: sessions have ended about 12 h after the VPN session began.

**Renew all…** (Sessions card, and the Reconnect… menu) is a confirmed forced sign-in of every enabled cluster (`AppModel.renew`). On the rash route the first cluster's jump leg runs with `HPC_RENEW_JUMP_HOST=1`, so the shared jump master is replaced too. That drops every tunnelled cluster, which the same chain then signs in again over the new one. Cost: one Duo push per leg (rash, AIRE, Calder), one at a time. Everything riding the old sessions closes first, shared `ssh` commands included. If the 12 h limit comes from the VPN, renewing SSH does not extend the VPN itself; reconnect the VPN first, or use the rash route off-VPN.

### Drops on a Mac that moves around

- `ConnectivityMonitor` (wake notifications and `NWPathMonitor`) has every session checked a few seconds after wake or a network change, instead of at the next, possibly backed-off, refresh. Dead links go in the same pass.
- A session that was live and loses its master, or stops answering three times, gets `ClusterSession.droppedAt`. A Disconnect, route change or failed sign-in never does. The app posts "<cluster> session dropped after N h" and the Sessions card shows when it dropped and how long it had lasted.
- **Sign in again after a drop** (default on) lets `AutoReconnectPolicy` queue a plain sign-in, reusing any master that survived. Every condition must hold: a saved Keychain password that was not rejected, keyboard or mouse input in the last two minutes, and a usable network. Each cluster gets at most three attempts per drop, 150 s apart (ssh closes a dead master within five minutes). After a declined or unanswered push, a rejected or expired password, a rash failure or Cancel sign-in, nothing is retried until the user signs in themselves.

## Runtime Layout

All paths are relative to the project root unless they start with `~`.

```text
.runtime/preferences.json                         global, password-free preferences
.runtime/clusters/<id>/latest_snapshot.json       newest good snapshot (compact JSON); the widget reads it, and writes it after a fallback collection
.runtime/clusters/<id>/snapshot_history.jsonl     trend points, one per line (newest 1440 kept)
.runtime/clusters/<id>/job_state.json             job-state baseline for notifications
.runtime/clusters/<id>/collector.json             password-free {updatedAt, script, arguments} for the widget fallback
.runtime/clusters/<id>/app_state.json             widget lease {updatedAt, enabled, paused, live, refreshInterval}
.runtime/clusters/<id>/login_debug.log            per-login transcript (app + expect helper), 0600
.runtime/clusters/<id>/master_ssh.log             this cluster's ControlMaster output, 0600
.runtime/clusters/<id>/master-<socket name>.pid   pid of the master on that control path (one per route and account)
.runtime/clusters/<id>/askpass.fifo               exists only while a sign-in waits for ssh
.runtime/clusters/<id>/askpass.events             fixed words recorded by askpass during the last sign-in (no secrets)
.runtime/clusters/<id>/askpass.log                opt-in redacted askpass log (HPC_DEBUG=1 only)
.runtime/AIREMonitorApp.app, AIREDesktopWidget.app
.runtime/swift-build.log, swift-widget-build.log  build logs, rewritten by every build
.runtime/widget-launcher.log                      output of the last Widget-button launcher run
.runtime/.build_bundle.lock                       one build of this checkout at a time
.runtime/installed_app_path                       path of the installed app (scripts/install_app.sh), one line
.runtime/.install_app.lock                        one install of this checkout at a time
.runtime/previews/                                default output of scripts/render_previews.sh

~/.ssh/ctl/<id>-<sha256(user@host:route)[:12]>.sock    cluster ControlMaster; route = "direct" or "via-<jump host>"
~/.ssh/ctl/jump-<sha256(user@jump host)[:12]>.sock     rash jump master, shared by every cluster
~/Library/Application Support/LeedsHPCMonitor/app.lock  single-instance lock
```

**`app_state.json`** (HPCCore `ClusterAppState`) is the app/widget contract: `updatedAt` (ISO 8601 in UTC, no fractional seconds), `enabled`, `paused`, `live` (enabled and signed in) and `refreshInterval` (the current interval, backoff included). The app writes it atomically at session start, on every enabled, paused or live change, after every refresh attempt and on the 30 s heartbeat. At quit it is deleted for enabled, unpaused clusters and kept, with `live: false`, for paused or switched-off ones. The widget treats a record as current for max(90 s, 3 × `refreshInterval`) and honours `paused` and `enabled: false` at any age.

The jump leg logs to the `login_debug.log` of whichever cluster triggered it. A cache file that no longer decodes is moved aside to `<name>.bad` instead of being silently overwritten, and a malformed history line costs one point, never the whole history. The keepalive files of older releases are no longer written; the scripts retire old shared pid files when they cannot belong to another route.

Control sockets live in `~/.ssh/ctl/` (mode 700) with short SHA-256-based names. macOS caps Unix domain socket paths at 104 bytes and ssh appends a random suffix during setup, so socket paths must stay short and independent of how deeply the project is nested. Do not move them to long project-relative paths. Because each target socket name includes the account, host and route, AIRE and Calder never share a master, and each route has its own.

**Legacy migration.** On first launch, `PreferencesStore.load()` moves the single-cluster `latest_snapshot.json`, `snapshot_history.json` and `job_state.json` from `.runtime/` into `.runtime/clusters/aire/`, never overwriting files that already exist there. If there is no `preferences.json` yet, the old `connection_profile.json` supplies the starting values: username, jump host, AIRE's host, and the rash route if the old profile used the jump host (an old alias-mode profile becomes the direct route). A `snapshot_history.json` array is read once and replaced by `snapshot_history.jsonl` on the first rewrite. The socket key format is unchanged byte for byte, so an `aire-<hash>.sock` or `jump-<hash>.sock` master started by an old build is still found, and adopted.

## Snapshot Collector Contract

`scripts/hpc_snapshot.py` is cluster-agnostic. One invocation collects one cluster over that cluster's existing ControlMaster. It never prompts for, receives or forwards a password, never writes remote files, and only runs read-only commands. `MonitorService.collectorArguments(settings:)` builds its argv, and the same list is saved to `collector.json`:

```text
--cluster-id <id> --cluster-name <name> --username <user> --hostname <login host>
--jump-hostname <jump host> --use-jump-host|--no-jump-host
--control-path <cluster socket> --storage-spec '<JSON>' --timeout 30
[--jump-control-path <jump socket>]                (rash route only)
[--skip-storage]                                   (most of the app's own runs; never in collector.json)
```

- `--timeout` is the budget for the **whole** collection: the socket probe plus the round trips. The app runs the collector under a 40-second watchdog, the widget under 50 seconds. Before collecting, the script probes the master locally with `ssh -O check`, so a dead session produces an immediate "connection lost: SSH control master is not running" error.
- **One read-only round trip (rarely two).** Sections run in the order `remote`, `partitions`, `nodes`, `jobs_json`, [`jobs`], `node_details`, [`job_details`], `storage`, delimited by `=====HPC-SECTION:<name>=====` and `=====HPC-STATUS:<name>:<rc>=====` markers. Jobs come from `squeue --json`, whose times are rendered zone-less in the clusters' zone (Europe/London; `HPC_CLUSTER_TZ` overrides), as `SlurmTimestamp` reads them, so ages stay right on a Mac in another zone; the pipe-format listing and the per-job `scontrol show job` loop run only when the JSON is unavailable, plus a rare second, jobs-only round trip when the JSON arrives but cannot be used locally. The core (`remote`, `partitions`, `nodes`, and jobs from usable JSON or a clean pipe listing) decides whether the snapshot is good: its failure is an **error**, so an unusable job listing fails the refresh instead of showing an empty queue (the app keeps the previous job list). Enrichment (`node_details`, `job_details`, `storage`) only adds detail, and its failure is a **warning**.
- `--storage-spec` is the profile's `StorageVolumeSpec` list as JSON: `[{"label": "Scratch", "paths": ["/scratch-calder/users/$USER", "/scratch-calder/$USER"], "quota": "lustre", "optional": false}, …]`. `$USER` and `$HOME` are the only tokens, expanded on the login node; everything else is shell-quoted literally. The first candidate that is an existing directory wins, and each existence probe is time-limited, so a hung filesystem is reported rather than waited on. `quota` selects the method: `nfs` (`quota -s -w`, falling back to `quota -s`), `lustre` (`lfs quota -p <id>` when `lfs project -d` reports a non-zero project id, otherwise `lfs quota -u $USER`, raw output) or `none` (`df` only). An optional volume is omitted only when proven absent; one whose output was cut short is reported as `unavailable` / `not-collected` with `optional: true`. Storage runs last, so a stalled filesystem costs only the storage rows, and a `ps`-based guard skips storage (with a warning) while a `df`/`quota`/`lfs` from an earlier refresh is still stuck.
- **`--skip-storage`** leaves storage out. `storage: null` always means "not collected" (skipped, the stuck-storage guard, or the budget ran out first), so a consumer keeps its previous rows; `[]` means collected, no volumes. `storage_skipped` is true when storage was skipped on purpose or by the guard.
- **Output** is one JSON object on stdout: `schema_version` (1, the first key), `collected_at` (taken when the round trip returns), `started_at` (before the socket probe), `duration_ms`, `timings` (per round trip and per remote section), `cluster: {"id", "name"}`, `remote`, `jobs` (with `array_job_id`, `array_pending_tasks`, `array_throttle` and `pending_task_count` for arrays), `partitions`, `nodes`, `storage`, `storage_skipped`, `errors` and `warnings`. Each storage row has `label`, `path` (the **resolved** directory), `filesystem`, `source`, used, quota, limit and available size in GiB (the `*_gb` fields), `used_percent`, file count, quota and limit, `over_quota`, `quota_type` (`nfs` / `lustre-project` / `lustre-user` / `df`), `project_id`, `mount`, `unavailable_reason` and `optional`. HPCCore decodes every field leniently; a newer `schema_version` produces a warning, not a failure.
- The script exits 0 when `errors` is empty and 1 otherwise. Its unit tests live in `scripts/tests/test_snapshot.py` (`--self-test` runs them). `Tests/Fixtures/collector_snapshot.json` and `collector_contract.json` pin the contract; regenerate them with `python3 scripts/tests/test_snapshot.py --write-fixture`.

See [MONITORING_PROTOTYPE.md](MONITORING_PROTOTYPE.md) for the collector's command list and JSON details.

## Job Resource Use

With **Sample** on (Jobs → Resource use; default on), a refresh adds the collector's `--job-usage` section once a minute while one of the user's jobs runs (`ClusterSession.wantsJobUsage`; a manual Refresh always). The section lists running jobs (`squeue -t R -o '%A|%i|%N'`) and their per-node allocation (`scontrol -d show job`: `CPU_IDs`, `Mem`, GRES `IDX`). It then reaches each node with ssh from the login node, in parallel and bounded at 12 s each, at most 24 nodes. `pam_slurm_adopt` admits the user only where they have a job and adopts the session into one of them. On the node a short probe:

- reads every listed job's cgroup v2 counters twice, a second apart: `cpu.stat` `usage_usec` for CPUs busy, `memory.stat` `anon`, `memory.current`, `memory.peak` and `memory.max`;
- runs one `nvidia-smi --query-gpu=minor_number,...` query in between.

GPUs are attributed by minor number against Slurm's IDX. Only the adopted job's GPUs are visible, so on a node running several of the user's jobs the others' GPU figures are reported as missing, with a note. Nothing is started in a job (no `srun` steps) and nothing is written on the node. The probe's `nvidia-smi` and `sleep` run about a second inside the adopted job's cgroup (tens of MB). The section is never part of `collector.json`, so the widget's own collections stay on the login node.

`snapshot.job_usage` holds one row per (job, node): `null` when not sampled, `[]` when sampled with nothing running. The session keeps the rows itself (`jobUsage`, keyed by `Job.jobId`) with a two-hour trend per job (`JobUsageHistory`). The Jobs tab shows a card per running job: a verdict (well used, N of M GPUs idle, partly used, mostly idle), GPU utilisation, GPU memory, CPUs busy against allocated, memory against the limit, and the trend. The job sheet adds per-node and per-GPU rows (memory, power, temperature) and a chart. Sampling off clears the figures.

## Terminal

The Terminal tab of each cluster embeds real SSH sessions (SwiftTerm's `LocalProcessTerminalView`). Sessions are plain `/usr/bin/ssh -tt` child processes that **multiplex over that cluster's ControlMaster**, so opening a terminal never re-authenticates and never prompts for a password or Duo:

```text
ssh -tt -S <cluster socket> -o User=<user> -o BatchMode=yes -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no -o ConnectTimeout=5 -o ControlMaster=no <cluster host>
```

Before starting a session, the app pre-flights the master with `ssh -O check`. If the master is gone, it prints "<Cluster> SSH session is not running — use Connect for <Cluster> in the sidebar first." inside the terminal instead of launching ssh. **The app never types passwords into a terminal.**

Each cluster has its own `TerminalManager`, so an AIRE shell can never ride on Calder's session or the other way round. Its tabs survive switching dashboard tabs and switching clusters, and the cluster's accent colour tints the chrome.

- **Session cap.** At most 6 running tabs per cluster (`TerminalManager.maxConcurrentSessions`): sshd's MaxSessions, assumed to be OpenSSH's default of 10, minus one collector session, one file-browser command and two concurrent transfers. A seventh tab is not started; a banner says so and offers to close running log tails.
- Quick-command chips come from the profile: `squeue --me`, `sinfo`, Quota, `sinfo -N -p <gpuPartition>` (only if the profile has a GPU partition), and `htop || top`. The Quota command is built from the profile's storage specs, the same ones the collector gets: `quota -s` for the NFS home, and for each Lustre space its candidates in order with the collector's rule (project quota when the directory has a non-zero project id, else the user quota). A chip types into the active live shell when that is safe and the shell belongs to the same cluster, and otherwise runs in its own reused tab. `htop` always gets its own session.
- The Jobs detail sheet offers **Tail output**, which opens `tail -n 200 -F '<stdout path>'` on the job's cluster (reusing that job's tab; disabled while the job is pending and absent for an array's pending remainder), and **Cancel job** ("Cancel queued tasks" for a remainder), which runs `scancel` on that cluster only, after a confirmation, with the result shown inline.
- The Nodes tab offers **Open shell on login node**, which focuses an existing live shell or opens one.
- An exited session can be restarted with the cluster's current settings. **Closing a session terminates its ssh child**, so closed tabs never leave orphaned `ssh` processes behind; closing a connected shell or command asks first (with a "Don't ask again" option), while a log tail closes without asking.

## Files

Each cluster has its own file browser. `FileBrowserModel` (UI state) is created by the cluster's `ClusterSession` and attached to it once, so a path, history entry, preview or transfer can never be replayed against the other cluster's filesystem. Every operation captures the session's `ConnectionSettings` when it starts. Navigation history, listings and transfers survive tab and sidebar switches. All remote I/O goes through `RemoteFileService`, which runs every command through `MonitorService.runRemoteCommand` / `runTransfer`. Those pre-flight the ControlMaster, so a dead session fails instantly with a readable error. Every operation is user-initiated.

- **Shortcuts.** The chip row shows Home first, then the cluster's storage spaces from its latest snapshot (home, scratch, flash order, deduplicated by path). Home is the remote `$HOME`, resolved with `realpath` on the login node and never derived from a `/users/<name>` pattern; until that resolution has happened, the snapshot's home row stands in. The other chips use the **resolved** directories the collector reported verbatim. Rows marked `unavailable`, or still holding a `$USER`/`$HOME` template, get no chip. Only snapshots cached by the single-cluster collector (no `cluster` block, no `quota_type`) may name a filesystem root, and for those the username is appended. The tooltip says whether a space is the shared home or cluster-only, with its Lustre project or user quota.
- **Listing protocol: `ls` is never parsed.** Listings run an embedded Python script on the login node: `python3 -I -c <script> <path> …`, preferring `/usr/bin/python3` (3.9 on Calder) over whatever a user's conda or module setup puts first on `PATH`. Isolated mode (`-I`) ignores `PYTHONPATH` and user site-packages and keeps the home directory off `sys.path`, so a stray `~/json.py` cannot shadow a standard module. The scripts are limited to Python 3.6 features, take paths as `argv` elements and answer in JSON. Undecodable names are shown with U+FFFD and refuse every action except Copy Path. Listings are capped at 4000 entries in folders-first natural order; the filter field then searches the whole folder on the server. Returning to the tab refreshes a listing older than 15 s.
- **Identity reset.** The browser tags its open folder with the account and login host it was listed under (the route is deliberately not part of this identity). When the Files tab appears, when the session signs in or out, and after a route change, `reconcileConnectionIdentity()` drops the folder, history, selection, filter and open dialogs if they belong to a different identity. The cached home is likewise only reused for the identity it was resolved for. Transfers already running keep their own settings.
- **Operations.** New folder, rename (refused if the target exists, including a broken symlink; not offered for a `.aire-trash` folder or anything in one, whose runs the Trash sheet manages), upload and download, a text preview (up to 256 KiB, from the head, or from the end for `.out`, `.err` and `.log`; `file --mime-type` with a content sniff when `file` is missing), folder size (`du -shH`, which follows a symlinked folder such as `~/scratch` itself but not the links inside it), Copy Path, drag-and-drop upload, **Open Shell Here**, and **Open in Terminal** (vim, or `less +G` from the end). Uploads refuse to overwrite an existing remote file, and folders are not uploaded. Downloads go to `~/Downloads` under a unique name and are revealed in Finder.
- **Transfers.** At most two run at once per cluster (`FileActivity.maxConcurrentTransfers`); the rest wait in the transfer strip. Each is a local `/usr/bin/scp` with the `SSHMuxOptions` client options, so it never prompts and never becomes a master; the remote spec is a single argv element after `--`. A transfer writes a hidden `.<name>.part-xxxxxxxx` sibling first: a download replaces its reserved placeholder only when complete, and an upload is linked into place with `ln`, which atomically refuses a name that appeared meanwhile (`mv -n` where hard links are unsupported). No data for 120 s ends a transfer; the absolute ceiling is 10 minutes plus the time at 50 KB/s (a day when the size is unknown). Cancelling or quitting removes the partial files.
- **Server-side bounds.** Every remote command runs under GNU `timeout -k 5 <s>` on the login node as well as a local watchdog, because killing the local ssh does not stop a remote command that has no pty. Argument lists too long for one command line (a select-all of thousands of files) are staged as `/tmp/hpc-monitor-args-<uuid>` on the login node, which the script reads and deletes.
- **Remote contract.** An sh-compatible login shell, GNU coreutils (`timeout`, `stat -c`, `du`, and `mkdir`/`mv`/`ln`/`rm` with `--`) and Python 3.6 or newer. `file(1)` is optional.
- **Trash-first deletion.** **Move to Trash** (after a confirmation) moves items into a fresh `.aire-trash/<timestamp>-<id>/` run folder, named in cluster time (Europe/London), with `os.rename` only, so a move can never copy. Items on the home filesystem go to `~/.aire-trash`, which is the same folder on AIRE and Calder. Items on another filesystem (AIRE `/mnt/scratch`, Calder `/scratch-calder` and `/flash-calder`) get a `.aire-trash` folder beside them, so they never fill the small shared home quota; they keep counting against their own filesystem's quota until the trash is emptied. Each run folder carries a `.manifest.json` (original paths, cluster, time); the names `.manifest.json` and `.manifest.json.tmp-<digits>` (the manifest and its temporary file) are reserved there, so a user item with one of them gets a number (`.manifest (2).json`, `.manifest.json (2).tmp-123`), while a look-alike such as `.manifest.json.tmp.bak` keeps its name. Run folders beside scratch or flash items are indexed in `~/.aire-trash/.index/`, so they can be found from either cluster. If no trash folder can be created beside an item, nothing is moved: the app offers to copy it into the home trash (showing the measured size, and only when it fits), delete it permanently, or cancel. The trash is never emptied automatically. The name `.aire-trash` is kept from the single-cluster release.
- **Trash sheet.** Lists this cluster's trash runs (the shared home trash plus the indexed run folders), with Show, Restore per item or Restore All (runs trashed by older versions have no manifest and must be restored with `mv`), Calculate Sizes (a bounded `du -sk`), and Empty per run or for the whole trash through the permanent-delete path. An index entry is dropped only when the run is provably gone: Restore emptied and removed it, the app's own permanent delete (Empty, or Delete Permanently on the run folder) removed that exact run folder, or the user chose Forget while it was missing. Any other run whose folder is not at its path is listed as missing, whether its holder, its `.aire-trash` or the run folder itself was renamed, moved or trashed, or it was deleted outside the app. Renaming it back brings it back, and Forget drops only its index entry, deleting nothing. A run that cannot be reached (an I/O error, or a storage root not mounted on this login node) is listed as unavailable. Unreachable runs are never measured, restored or emptied.
- **Permanent delete and long copies.** `Delete Permanently` (after two confirmations) and a confirmed copy into the home trash run **detached** on the login node: a worker in a private `mkdtemp` folder (`hpc-monitor-op-*` in the login node's temp directory), in its own session, deleting in batches of `rm -rf --` (or copying with `cp -a` to a `.partial` name before renaming). The app polls it for progress and offers Cancel (SIGTERM to its process group); it survives timeouts, a dropped connection and quitting the app. A cancelled delete may leave the item it was on partly removed. A cancelled copy stops its running `cp`, but the `rm -rf` of an original (or of a `.partial`) runs in its own session and finishes, so an original is never left half-deleted; the cancelled banner lists any other failure as an error.
- **Protected paths.** Trash and permanent delete refuse non-absolute paths, paths with `.`, `..` or empty components, top-level folders (`/`, `/users`, `/mnt`, `/scratch-calder`), and home, every storage root and every ancestor of one (`/mnt/scratch`, `/scratch-calder/users`). The login-node scripts repeat the check against `realpath`'d roots, and items already inside a trash folder cannot be trashed again.
- **Injection defences.** Remote names are untrusted data. Every interpolated value is single-quoted (`'` becomes `'\''`), and path arguments follow a `--` separator.
- **Integrations.** **Browse workdir** in the Jobs sheet opens the job's working directory in that cluster's Files tab.

## Desktop Widget Data Flow

The widget is a separate process. It shares `HPCCore` with the app (snapshot schema, job and node state rules, GPU accounting, timestamps, defaults, cluster identities, and its own feed and collector policy), but no app code. Its primary data path is **file watching, not SSH**.

- **Discovery.** It lists `.runtime/clusters/` every 2 seconds, also watches that directory, and keeps one feed per directory whose name is a valid cluster id. Clusters whose `enabled` flag is `false` in `.runtime/preferences.json` are not followed; the widget reads only those flags, and an unreadable file hides nothing. Feeds are sorted in `ClusterIdentity` order, then alphabetically. The window grows by one row per cluster, up to 4 rows, and the footer mentions any rows that do not fit.
- **Who owns collection.** Each feed reads the cluster's `app_state.json`. `enabled: false` shows the row as off and `paused: true` as paused, whatever the record's age. Otherwise a record written within max(90 s, 3 × `refreshInterval`) (and at most 120 s in the future) means the app is running and owns the cluster: live, or retrying ("<X> is not connected in Leeds HPC Monitor…"). In all these cases the widget never collects. Decoding is lenient: missing flags mean enabled, not paused and not live, and an unparsable `updatedAt` falls back to the file's modification date.
- **Primary path.** Each feed watches its cluster directory, because the app replaces `latest_snapshot.json` atomically, which shows up as a directory event, and reloads the file whenever its modification date changes. A snapshot collected at most 30 seconds ago is shown as live.
- **Fallback collection, per cluster.** Only when no current lease exists and the snapshot is missing or older than 30 s (or the widget's own data is over 10 s old). The widget loads `collector.json` and validates it: it must decode, its `--cluster-id` must match the directory, and the recorded script must be a relative path inside the project (no `..`, no absolute or `~` path, no symlink resolving outside the checkout) that exists. It runs nothing when the `--control-path` socket is missing. Then it runs `/usr/bin/python3 <script> <arguments>`. At most one collection per cluster runs at a time, attempts are at least 10 seconds apart (manual ones too), and after failures the next automatic attempt waits 10, 20, 40, 80, 160, then 300 s, which a manual Refresh skips once. The watchdog is the recorded `--timeout` (default 30, clamped to 1–300) plus 20 seconds, so 50 seconds with the app's arguments: SIGTERM, then SIGKILL 3 seconds later, and output pipes still held open 3 seconds after the child exits no longer block completion. Only a clean result is accepted: exit 0, valid JSON, no collector errors, no timeout, and a matching `cluster.id`. The result is dropped if the app took over meanwhile, a snapshot file someone else wrote during the collection is never overwritten, and an app-written file that does not decode is reported, not collected over. Otherwise the widget atomically writes the collector's stdout to `latest_snapshot.json`. The collector's "control master is not running" becomes "Sign in to <cluster> in Leeds HPC Monitor to refresh." The collector never authenticates, so all of this works only while that cluster's master is still alive (within its 24 h idle limit). Without `collector.json` the row says to connect the cluster in the app.
- **States.** Each row is `connecting`, `live`, `cached` (snapshot older than 30 seconds), `offline` (no snapshot and an error or notice), `paused` or `off`. Cached, paused and off rows are muted and show a relative age, orange under an hour and red from an hour. The header chip counts clusters ("all 2 clusters", "1 of 2 live") and never sums their numbers. The footer reads "Data from <oldest live collection time>", a manual Refresh always answers there, and every per-cluster error is prefixed with the cluster name.
- **Rows.** Each row covers one cluster: its name and monogram in its accent colour, a status chip with the login node (collector warnings go in its tooltip), the snapshot time, its GPUs ("free" counts idle GPUs a new job could start on, one figure per model, such as "2 + 1" under "H200 + L40", and "?" in grey, never the orange of a full pool, when nothing is known idle only because allocation is unknown; the usage ring reads "?" in grey while any GPU's allocation is unknown, since a partial count would understate the load; the bar separates stranded, unknown and unavailable GPUs; ring, bar and heatmap use the app's occupancy colours: allocated cyan, partly allocated pale cyan, free green, unavailable grey), Run and Wait counts plus a grey Held pill while any job is held (Wait counts every task of a pending array and never a held job; suspended jobs count as neither), a grey "N down" for GPU nodes that accept no work, the first running or pending job, and a GPU-node heatmap. Job and node identities are qualified by cluster.
- **Window.** A borderless, movable panel at desktop-icon level on every Space. The frame is saved under the pre-rename autosave name `AIREDesktopWidget`, and when rows are added or removed the top edge stays put. The context menu offers Refresh all, per-cluster refresh, Open Leeds HPC Monitor (brings a running app, bundle id `local.aire.monitor`, forward. Otherwise, when `.runtime/installed_app_path` names a bundle with that identifier, it opens that installed app through `NSWorkspace`, without rebuilding. Otherwise it runs `scripts/run_macos_app.sh`, which rebuilds only when the sources changed and then opens the app, so it never opens an outdated `.runtime/AIREMonitorApp.app` directly. Exit 75 is reported as another build running) and Quit.
- **Diagnostics.** `log stream --predicate 'subsystem == "local.aire.desktop-widget"'`.

The main app's sidebar and its menu bar both have a `Widget` button that opens it.

## Overview

The overview is the default landing page (`OverviewDashboard`). Two rules shape it: numbers from different clusters are never silently added together, and a cluster without a snapshot shows an explicit "not connected" or "off" state, never zeros. Top to bottom:

- **Header**, with **Refresh all** (⌘R), enabled only when some cluster can refresh.
- **Needs attention**, per cluster, most severe first: a refresh failure by what can fix it ("Setup problem", whose help says signing in again will not help, or, for a cluster that is not live, that signing in will not fix it; "Slurm not answering"; or "Refreshes failing" for two or more connection failures while the cluster still reads as live) or an error from a user action (a failed sign-in, job cancel or sign-out is named by its own first line; a manual refresh keeps its refresh wording); storage over quota or at 90 % of space or file count; jobs whose dependency can never be satisfied; held jobs; GPU models with no usable node (grey, like that pool everywhere else). Each item opens its cluster, on the relevant tab where there is one.
- **Combined jobs**: the user's jobs from every reporting cluster, each tagged with its cluster; the header counts running, pending and held jobs apart. Each cluster keeps the Jobs tab's order, and the clusters are merged by group (running, then waiting on resources, on a dependency, held) and then by submit time, never by job id: ids from two controllers are not comparable. Job identity is cluster-qualified, and a held job reads "Held" in grey, as on the Jobs tab. The list is capped at 8 rows until expanded; when a queued array remainder stands for several jobs, the button counts rows and names the job total ("Show all 9 rows (65 jobs)"). Clicking a job opens its cluster's Jobs tab with the detail sheet.
- **Cluster cards**, one per cluster in catalog order: identity, connection state with its one action, snapshot age, a jobs tile (running, with pending and held apart), idle capacity per GPU model in the shared pool tone (see [Current Views](#current-views)), each model with the full breakdown of the GPUs that are not idle under it ("34 in use · 7 stranded · 15 unavailable", or "all 3 unavailable"; "?" when nothing is known idle only because allocation is unknown, also in the "+N more models" tooltip, and the caption then names the unknown GPUs, "56 unknown" or "3 in use · 8 unknown", never a bare "0 in use"), and storage rows. The home row is marked "shared by all clusters".

## Menu Bar Monitor

While the main app runs, it installs a native AppKit status item (`StatusBarMonitorController`) that summarises every enabled cluster:

- **Title.** Built from **live** clusters only; cached or paused figures may describe jobs that ended hours ago, so they are named, with their time, in the tooltip instead. A live cluster whose Slurm is failing (`schedulerIssue`) counts as not live here, because its figures are only carried forward. `C · train 9h 29m` (monogram, job name middle-truncated to fit, elapsed) when exactly one job is running across live clusters; `3 jobs` when several are; otherwise each live cluster's largest GPU pool, such as `A 6 · C 27+` (`A ?` while nothing is known idle only because allocation is unknown; `+` when another model also has idle GPUs, which a pool of unknown allocation never earns; pools are never summed); otherwise a state word (`Signing in`, `Checking`, `Syncing`, `Ready`, `Slurm error`, `Cached`, `Paused`, `Offline`, `Off`). The width is reserved from a digit-stable template, so the item does not jitter on every tick.
- **Icon tint** shows combined health: green when every enabled cluster is live with Slurm answering; orange when only some are (a Slurm error included), or a check, sign-in or first collection is running; red when nothing is live or shown and a cluster reports an error; dimmed when only cached or paused figures exist, or nothing is connected. With every cluster off, it is a plain template icon.
- **Tooltip**: one block per cluster (connection state, sign-in progress, job counts with held jobs named apart from pending ones, one line per GPU pool such as "H200: 0 of 56 idle · 34 in use · 7 stranded · 15 unavailable", storage pressure; figures that are not live carry their collection time, and a Slurm-error cluster's counts are marked "(not current)"), then the shared home quota once.
- **Dropdown** (`MenuBarMonitorView`): a combined header, then one compact section per cluster with its state pill, a single action (Connect, a plain sign-in; Resume; or turn monitoring on), the job counts ("9 running · 1 pending · 11 held") over the first three jobs, then "+N more", or "+37 more jobs in 16 rows" once a hidden array remainder stands for several tasks, so the rows and the count line add up, then GPU pool and storage meters. A GPU row reads "K of M idle" in the shared pool tone beside the overview's segmented capacity meter, with the GPUs that are not idle under it ("34 in use · 7 stranded · 15 unavailable"); when nothing is known idle only because allocation is unknown it reads "? of 9 idle" in grey over "9 unknown". A Slurm-error cluster's section hides "Updated N ago", greys its figures and shows a warning row ("… — showing the previous figures"). Storage rows use the Storage tab's tone: warning from 75 %, critical from 90 % or over quota, judged on the larger of space and file count. The shared home appears once below the sections, then any app-level error, then footer actions: Refresh all (enabled only when some cluster can refresh), Dashboard, Widget and Quit (which still goes through the quit prompt).
- **Opening the menu** calls `refreshAllQuietly()`, which honours pause, skips clusters never signed in or signed out with Disconnect, and never surfaces an error, so a glance shows data at most a few seconds old without starting a sign-in.

The status item and the dropdown are both built from one `MenuBarDigest`, so the title and the panel beneath it never disagree. The item is only touched when its visible signature changes, and the dropdown re-renders only while it is open.

## Current Views

The dashboard window is a `NavigationSplitView` with a minimum size of 1000 × 680 (`ContentView.minimumWindowSize`) and a 340 pt minimum sidebar; the layout tests hold every tab to the resulting 660 pt detail column. While the window is closed, or fully hidden for 5 seconds, its SwiftUI tree stops rendering.

**Sidebar**, top to bottom: the app header; the cluster switcher (Overview, then one row per cluster with its state pill, two summary lines, the queue ("9 running · 1 pending · 11 held") and the largest GPU pool ("0 of 56 H200 idle · +1 more model", "? of 84 L40S idle" while its allocation is unknown), and Connect, Turn on or Resume; the tooltip adds the shortcut and every pool); per-cluster sign-in banners, each with Cancel; app-level errors (dismissable); the selected cluster's session panel (status, staleness, Pause/Resume, Reconnect…, Disconnect, collector warnings, errors); the sign-in card (route, username, password, Remember in Keychain with the forget offer and a flag for a rejected saved password, Duo option and a Duo route hint, the "Changes apply at the next sign-in…" hint, and an Advanced section with per-cluster on/off toggles and hosts, the jump host and the project root), which collapses to "Signed in as <user>" once every enabled cluster is live; the actions (Connect / Connect all, or Cancel sign-in; Refresh; Widget, with progress while it builds; the Reconnect… menu); and notifications (the GPU-free toggle and the permission state with Request permission or Open System Settings).

**Cluster dashboard.** One pinned header row: badge, name, host · user · "updated N ago" (or "cached data from …"), idle GPU chips per model ("1 of 84 L40S idle", or "? of …" in grey when nothing is known idle only because allocation is unknown, as in the "+N" tooltip of models that do not fit; dropping to one chip, then none, when narrow), the connection pill, Refresh (⌘R) and the ⋯ session menu (Pause or Resume monitoring, Reconnect…, Disconnect…, Turn off monitoring). Below it sit the status strip and a tab bar whose badges replace the old summary tiles: Jobs (count), Nodes (nodes accepting no work), Storage (the fullest space once it reaches 75 % or goes over quota) and Terminal (open tabs). A cluster with no snapshot, no live session and no open terminals (or with monitoring off) shows the connect hero instead of zeroed metrics. Its three steps lead to a sign-in and end with the refresh cadence (jobs, GPUs and nodes every 10 s; storage every 5 min, and on every refresh while the Storage tab is open). While the last refresh failed with a setup problem, the steps start with fixing it instead and Connect becomes a plain button: a sign-in before the fix still costs a Duo push and loads no snapshot. Once the session is live the tabs appear even before the first snapshot: Files and Terminal work at once, and the other tabs show a placeholder.

**Status strip** (`ShellStatusStrip.swift`), in priority order: a sign-in in progress, with Cancel; an error from a user action; the last refresh failure, from the first one on, worded by what can fix it (a setup problem on this Mac in red, "Signing in again will not help.", or "Signing in will not fix it." for a cluster that is not connected; Slurm trouble with the session still live in orange; connection trouble in orange, red after a manual refresh); then the phase (checking, not live, a Slurm issue, collector warnings). From the second failure in a row the hint starts with "Failed N times in a row." An inline Details disclosure shows the kind, the count, the time of the last attempt and the raw output. While paused, the strip keeps the last failure as "Before the pause: …".

Tabs:

- **Jobs**: summary metrics (Pending leaves held jobs out and adds them beside it, "+11 held") and job cards by state; a detail sheet (timeline, array, resources, paths) from `squeue --json`, with `scontrol show job` only on the collector's pipe fallback, plus Tail output, Browse workdir and Cancel job
- **Partitions**: cards styled from the profile's partition hints, counted by unique node, GPU capacity per model ("56 H200 + 3 L40"), node-state bars, time limits
- **Nodes**: GPU-first dashboard (allocation, idle GPUs by model, mixed and unavailable GPU nodes, slot-level occupancy) plus CPU, high-memory and teaching node classes where the cluster has them; while node details are missing (allocation unknown), the ring shows a dash instead of a share in use, a caption names the unknown GPUs and the GPU section's subtitle reads "? idle L40S"
- **Trends**: this cluster's own history over 1 h, 6 h or 24 h (a window shared with Storage): GPU availability and allocation with a per-model capacity signal (green with room; orange when tight or full, never red; grey when no node accepts work or the verdict cannot be judged), queue pressure (the headline is the current snapshot's "9 running · 1 pending · 11 held"; history points record only running and queued, so the line counts held jobs as queued), unavailable GPU nodes, and home, scratch and flash pressure in the Storage tab's tone. Each history point records GPUs of unknown allocation (`gpuUnknown`); while some are unknown the GPU charts leave a gap, the cards read "unknown" or "at least N idle", and the capacity signal reads "Allocation unknown" in grey whenever those GPUs could change its verdict (never "GPU full" merely because nothing is known idle)
- **Storage**: one card per reported space, with used percentage, headroom, limit, file-count pressure, and how it is measured (NFS quota, Lustre project or user quota, or filesystem totals from `df`)
- **Files** and **Terminal**, as above

Detail tables are hidden by default behind `Show Details`. State classification, GPU counting and time handling come from HPCCore; `SlurmFormatting.swift` holds the app-side state colours and formatting. Sizes are binary: storage (`formatGB`) reads "12.3 GiB", whole GiB from 100 GiB up to 10 TiB ("2,458 GiB"), then TiB, and node memory on the Nodes and Partitions cards (`formatMemoryGB`) switches to TiB at 1 TiB ("754 GiB", "1.5 TiB"). Nodes that accept no work (down, drained, maintenance) are grey everywhere, and so is a partition with no usable node; red is reserved for faults (failed jobs, critical storage, a partition Slurm reports down or inactive) and orange for warnings. Occupancy is capacity, not a status: allocated nodes are blue and mixed ones a paler blue, never orange. A GPU pool has one tone on every surface (`GPUPool.idleTone`: the overview tile, the cluster header chip, the menu bar row): green while some GPU is idle, orange when the pool is known to be full, never red, and grey when every node is unavailable or nothing is known idle only because allocation is unknown. The Trends capacity signal agrees (adding orange for tight capacity), and the Nodes ring is capped at orange. The visual language uses macOS system materials for the sidebar, cards, menu panel and widget shell, with each cluster's accent colour (AIRE green, Calder violet) on its badge, tabs and terminal chrome. Motion is restrained: hover lift on cards, smooth meter changes, and animated detail surfaces.

## Tests and Tooling

```bash
scripts/test_all.sh [swift] [collector] [login]          # every suite, with a PASS/FAIL summary
Tests/AIREMonitorAppTests/run_tests.sh [--filter <name>]  # Swift tests
python3 scripts/tests/test_snapshot.py                   # collector unit tests
python3 scripts/tests/test_login_flow.py                 # login scripts against a fake ssh
scripts/render_previews.sh [output-dir] [data-dir]       # offscreen PNG renders
```

- The Swift tests use swift-testing, because XCTest does not exist on a Mac with only the Command Line Tools. `run_tests.sh` builds in its own scratch directory (`hpc-monitor-tests-build` under the per-user temp dir; override with `HPC_TEST_BUILD_DIR`). On a Command Line Tools-only machine it adds `-F` and an rpath for the CLT's `Testing.framework`; without them SwiftPM's generated runner compiles its swift-testing entry point out and reports a "pass" with zero tests. `Package.swift` disables cross-import overlays for the test target only and links the test bundle for macOS 14; the app and widget still target macOS 13. With Xcode selected, the wrapper is equivalent to `swift test`.
- The tests link the app and HPCCore, not the widget (`test_all.sh` builds the widget separately). They need no network, Keychain or `~/.ssh`: sessions run on a fake `ClusterBackend` and a hand-driven `RefreshScheduling`, the file manager on a scripted remote runner, and files go to temporary directories.
- The "Minimum window layout" suite hosts every tab, sign-in screen, the overview and the status strip at the minimum detail column and fails on overflow. It needs a window server, so it runs in a logged-in session or on a CI macOS runner and is skipped elsewhere.
- `InstallTests` cover the checkout discovery (`HPCProjectRoot` included) and the install record. They also run the real `install_app.sh` in a throwaway checkout against small ad-hoc-signed fake bundles: install, unchanged and changed updates, a running copy that does not quit (and `--force`), a foreign bundle under the app's name, `--uninstall`, the same folder under another spelling, a failed first install, a failed swap (put back, or kept), the write-access check, reopening after a failure, leftover staging folders and the `~/Applications` fallback. The fake bundles' executable is a small compiled sleeper, so a running copy really runs from its bundle. They also cover running copies found through a link (to the folder or to the executable itself), another letter case, the recorded spelling, a folder with a non-ASCII name in the C locale, or only by the executable the kernel runs (started under a bare name), and processes that are not copies: a `tail -f` of the path, or one that only maps the executable. They cover `--uninstall` with a running copy, of a bundle the account cannot delete (locked, an ACL, a read-only folder inside: nothing changes, nothing is asked to quit), with a copy starting while the bundle is moved out of the way (put back, for `--uninstall` and for an update), after a run killed between its two moves and with only a leftover staging folder, an old install that cannot be deleted after a move (left whole), a live staging folder from another checkout, owner files of ended or reused process ids, a folder appearing at the install mid-swap, both kinds of exit 75, and what LaunchServices would list: the lsregister stub logs each bundle's inode, and replaying its `-f` and `-u` calls must leave exactly the installed copy (or, after `--uninstall`, the `.runtime/` bundle), with `.runtime/` unregistered last and only once nothing runs from it. The real `build_bundle.sh` runs with a fake `swift` to check its install-source mode. `HPC_INSTALL_DIR` (or `HPC_INSTALL_DEFAULT_DIR` and `HOME`) points at a temp folder, and `HPC_LSREGISTER`, `open` and `swift` are stubs, so they never touch `/Applications`, `~/Applications` or LaunchServices. A syntax check runs `bash -n`/`zsh -n` over every script.
- `CollectorContractTests` decode the collector fixtures in `Tests/Fixtures/`, check that every emitted field survives a round trip, and fail when the collector's constants drift from `HPCDefaults` or the catalog.
- `test_all.sh` gives each suite a time limit and runs every suite even when one fails. `.github/workflows/tests.yml` runs it on `macos-15`. See [scripts/tests/README.md](scripts/tests/README.md) for the Python suites.
- `render_previews.sh` runs the opt-in "Preview renders" suite (`HPC_RENDER_PREVIEWS`, `HPC_PREVIEW_DATA`). Output defaults to `.runtime/previews` and data to `.runtime/clusters`, falling back to checked-in fixtures, re-stamped to the current time. A relative output or data folder is resolved against the caller's working directory, and a data folder given explicitly must exist. It renders the overview, every tab, Nodes at 1100 and 1220 × 760, each tab's detail column at the minimum size, the menu bar dropdown, the job sheet (also for an array remainder), the sign-in states and the sidebar form, the status strip for each failure kind (with Details open, dark and light), a paused cluster's Trends, the setup-problem hero, and a Files tab over a fake remote. No render uses SSH or the Keychain or writes runtime state.

## Current Limitations

- The app bundles are generated locally under `.runtime/` and are not notarized. Without a code-signing certificate they are signed ad hoc, and Keychain asks again after each rebuild. The installed app is a copy of that bundle and still needs its checkout (helpers and `.runtime/`). Moving the checkout means running `install_app.sh` again.
- The rash route assumes one username for `rash.leeds.ac.uk` and every monitored cluster.
- It relies on `/usr/bin/ssh`, `/usr/bin/expect` and `/usr/bin/python3` locally; the Files tab also needs GNU coreutils and Python 3.6 or newer on the login node.
- Automated monitoring is read-only. The only write-capable actions are the user-driven Terminal, the Files tab and the confirmation-gated `Cancel job`.
- Passwords are stored in the macOS Keychain only when `Remember in Keychain` is enabled (the default; the choice is remembered).
- The refresh interval is fixed at 10 seconds (with backoff) and storage is refreshed about every 5 minutes. Final job states come from `squeue` only; `sacct` is not used yet.
- A cluster paused in the app stays paused in the widget, even after the app quits, until the app writes `app_state.json` again; a switched-off cluster stays hidden there.
- Switching from the rash route to direct does not close the shared jump master; it expires on its 24 h idle limit. Disconnect closes it when nothing else uses it.
- The terminal cap of 6 tabs per cluster assumes sshd's default MaxSessions of 10.
